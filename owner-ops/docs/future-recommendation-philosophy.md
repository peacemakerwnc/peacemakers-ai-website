# Future recommendation philosophy (Phase 1.1 boundary)

**Status:** Policy document + testable invariants. No recommendation engine in Increment 4.

## Preference order

1. Eliminate unnecessary work.
2. Simplify the process.
3. Improve use of existing software.
4. Use native features and configuration.
5. Connect existing tools.
6. Add a lightweight automation.
7. Add a new tool only when justified.
8. Use custom development only when simpler approaches are insufficient.

## Governing principle

Recommend the simplest reliable solution that creates meaningful client value and that James can personally implement, support, maintain, and explain.

## Every future recommendation must answer

- What problem does this solve?
- What evidence supports it?
- Can the current software solve it?
- Why is a new tool necessary?
- What will it cost?
- What complexity does it add?
- Can James implement it?
- Can James support it?
- What result should it create?
- How will the result be measured?
- What must be validated first?
- What assumptions remain?
- What source supports time-sensitive claims?

## Mission-aligned requirements

- Serve the client honestly
- Avoid unnecessary complexity
- Avoid inflated value claims
- Respect client resources
- Preserve human judgment
- Make limitations visible
- Distinguish facts, estimates, assumptions, and advice
- Recommend maintainable systems
- Avoid selling tools merely because they exist
- Require James’s approval before client delivery

Do not add forced religious language to ordinary client documents unless James explicitly chooses it.

## Increment 4 invariant

Automated or manual extraction may create **proposed** findings only. No path may create approved recommendations, SOWs, SOPs, ROI claims, or software shortlists in this phase.
